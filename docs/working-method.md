# 工作方法论(给 Opus 4.8 及后续强模型)

> 三层事实指引(../../CLAUDE.md → ../CLAUDE.md → fork-guide.md)告诉你**这个项目是什么、
> 有哪些坑**。本文回答另一个问题:**在这个项目里怎么干活**——任务怎么拆、
> 结果怎么验、下一步怎么选。每条方法都附本项目的真实案例,不是空谈。

---

## 一、怎么分解难任务

### 1.1 按"地基→楼层"分层,永远先正确性
本项目的固定层序:**排盘正确性 → 解读质量 → 产品体验**。理由:解读建立在盘上,
盘错全错;产品建立在解读上。历史路径完全按此走:P0(夏令时/边界预警/金标准测试)
→ 校准与用神 → K线/合婚/看板。接到"帮我优化"这类模糊任务,先按这个层序拆,
给用户一张分层表+推荐路线,再动手。

### 1.2 接手陌生代码 = 源码审计 + 黑盒实测,双管齐下
只读代码会漏运行时行为,只跑黑盒会漏结构性隐患。案例:审计 taibu 源码发现
"大运模块不接收真太阳时"(黑盒测不到,因为要特定输入组合);同时黑盒边界实测
抓到"晚子时两引擎日柱不同"(纯读代码很难注意到两库默认流派相反)。
做法:派 subagent 按清单逐文件审计(给出 文件:行号),自己同时写边界用例实跑。

### 1.3 动手前先找"金标准",没有就先造度量
每个大改动都要先回答:"我怎么知道自己做对了?"
- 有外部事实的:找它。乾隆帝史载八字验 1600 年下限;NOAA 官方值验均时差;
  独立第二实现(taibu/lunar-javascript)验四柱。
- 没有外部事实的(如强弱评分权重):**先建校准工具和标注数据集,再谈改动**。
  本项目先写 calibrate-strength.mjs + 61 例古籍命例,量化出"偏弱 4 分"之后,
  仍然只做了阈值层的 opt-in 模型,权重本体留待数据更多——这个克制是对的,照做。

### 1.4 区分"流派分歧"与"bug",处理方式完全不同
判据:**有没有客观对错标准**。晚子时日柱归属、强弱分档阈值是流派口径 → 做成
可选参数,默认不动;大运不吃真太阳时、日支帮扶漏计是 bug → 直接修。
把口径当 bug 修(或反过来)是这个领域最常见的错误。

### 1.5 大批量操作先小样冒烟
10000 样本差分先跑 2000;66 条古籍候选先人工读 6 条看误标模式,再定守卫规则。
冒烟的目的不是省时间,是**在便宜的地方发现贵的错误**(如 45ms/次的性能热点
就是 2000 样本冒烟时发现的,顺手做了 calculatePillars 快 48 倍)。

### 1.6 盘点既有资产,别重造
接到"加小六壬"时先 grep——发现引擎已有三种起卦方式,只差 UI。
新需求进来第一步永远是:core 里有没有?上游有没有?能不能组合出来?

## 二、怎么验证自己的工作

### 2.1 独立源交叉,一致才算数
重要结论必须两个以上**独立**来源印证:四柱=手算+双引擎三方一致才敢说对;
喜用神=引擎+《穷通宝鉴》调候规则命中才敢给用户;强弱=引擎分数 vs 任铁樵批语。
只有一个来源时,明确说"未交叉验证"。

### 2.2 跑之前先写下期望输出
"运行差分测试" → 先想好"期望:✅ 双引擎四柱完全一致,约 10s"。
"修日支帮扶" → 先想好"期望:用户盘 3.2 中和 → 4 分以上偏强"。
结果与期望不符时**停下来查根因,禁止编理由让自己过关**。fork-guide 的
工作流全部带期望输出,就是这个方法的固化。

### 2.3 数值先验方向,再看绝对值
K线评分出来第一件事不是看分数,是检查:丙午(双火喜用)年是不是高分?
乙卯(纯木忌神)年是不是低分?方向错=模型错;方向对但绝对值怪=参数问题。
任何打分类功能(强弱/K线/合婚)都先做方向性断言,测试里已有先例可抄。

### 2.4 "完成"的门槛是五件套
代码 + 测试(全量绿,不只新增的绿)+ 文档(口径/坑表同步)+ 推送 + CI 绿。
UI 改动追加第六件:真机跑通(preview 实测,不是"代码看起来对";
本项目曾靠真机测试当场抓到 sequence.end→result 的键名 bug)。
push 前本地预检 CI 的全部 job(lint/type-check/build/test)——lint 事件的教训。

### 2.5 失败时的怀疑顺序
测试/差分挂了:① 我刚改的代码 → ② 我对 API 的理解(回去读源码,别猜)→
③ 环境(镜像/缓存/type:module 这类)→ ④ 最后才怀疑 oracle/上游,且必须
找第三源仲裁(史载命例/权威万年历),不许单方面豁免。

### 2.6 诚实标注不确定性,写进交付物
1900 前排盘"经乾隆金标准抽验但未逐日核对";合成校准标签"仅冒烟用,
正式结论以古籍命例为准";每个功能页脚的"仅供文化研究与娱乐"。
不确定性是交付物的一部分——吞掉它=给未来埋雷。

### 2.7 踩坑当天入表
每个新坑在**当次会话内**写进 fork-guide 坑表(症状→原因→解法)。
坑表是活文档,它的价值取决于时效性。

## 三、怎么决定下一步

### 3.1 排序标准:单位成本买到的"长期保障"最多的先做
本项目的实际顺序及理由,可直接类比:
差分测试(一天,换永久回归安全网)→ P1 正确性(修完就是同类最严谨)→
产品层(用户每天用得到)→ 解读权重(最难且需要数据积累,最后)。
"难而收益后置"的事不是不做,是排在"便宜且保障性"的事之后。

### 3.2 用户话语的翻译规则
- "优化一下" → 拆层给表,附推荐路线,用户点头即按推荐走(见 1.1)。
- "能不能做 X" → 先 gap 分析(要什么 vs 有什么),给"缺的清单"而不是直接开写。
- "都做" → 建 TaskCreate 清单逐项推进,每完成一项立即验证并 commit,
  不要攒一个大提交(本项目单日最多 6 个独立 commit,各自可回滚)。
- 用户报 bug(如 CI 红)→ 修复 + 本地复现验证 + 把坑写进表,三件一起交。

### 3.3 顺手发现的问题,三分法
- 小且无行为变化(性能热点、命名误导)→ 当场修,单独说明。
- 大或有行为影响(权重再平衡)→ 记入待办与 ADR,**不顺手改**。
- 属于口径选择 → 做成参数,默认不动(ADR-3/ADR-4 先例)。

### 3.4 阻塞的标准动作:换路,不停车
网络挂 → npmmirror 镜像 / 重试 2-4 次 / r.jina.ai 换道读网页;
工具不可用(Chrome 扩展没连)→ 换验证方式(代码级核验/preview);
Node 下 require CJS 失败 → 复制 .cjs 验证。
原则:同一目标至少尝试两条独立路径后,才允许把"做不了"报给用户。

### 3.5 什么时候问用户,什么时候直接做
**问**:不可逆动作(关机、上游 PR 这类外发)、口径/偏好选择(以哪个为基准算)、
花钱或涉账号的事。**直接做**:可逆的、有既定先例的、用户已说"都做"范围内的。
问的时候给推荐项+理由,不要开放式甩锅。

### 3.6 每轮收尾的固定动作
① 任务状态更新;② 记忆文件更新(指针指向仓库文档,细节写在文档里——
记忆会过时,文档跟着代码走);③ 下一步建议(具体到"要不要我现在就 X");
④ 如果这轮产生了新方法论教训,更新**本文**。
